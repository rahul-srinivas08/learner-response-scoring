# AI collaboration log

Built with Claude Code (Sonnet 5) across all three parts and `REPORT.md` — every cell's output checked against what its markdown claims, not assumed from the code alone.

**How the code actually got made — the loop, not just the tool name:** every section of every notebook followed the same sequence, repeated dozens of times across the project: (1) instruction/feedback given — what to test, what finding to chase, or what was wrong with the last attempt; (2) Claude Code wrote and executed the cell(s); (3) the printed output was checked against what the cell's own markdown claimed, not taken on faith from the code; (4) either accepted as-is, or sent back for another round based on what the numbers actually showed. Longer-running steps (transformer training, the multi-variant backbone tests) were kicked off as background jobs so direction could continue on other sections in parallel rather than blocking on a single training run. Nothing in any notebook was written by asking the AI to "build Part 2" or "build Part 3" as one open-ended request — each result traces back to a specific instruction plus a specific number that either confirmed or contradicted it.

**Directed vs. AI-proposed, by part:** the core eval strategy (QWK/MAE, `false_praise`, the two ceilings, group-safe CV) predates this session, in `evaluation.py`. Within the session, Claude Code was used as a coding assistant — writing and running cells, executing longer experiments in the background while direction continued in parallel — but which questions got asked, when to stop trusting a first pass, and which finding mattered enough to act on came from direction, not from the AI running unprompted.

- **Part 1 was the most direction-heavy of the three, and that's underrepresented if this log only talks about Part 2/3.** `relevance_cosine_sim` showed weak feature importance despite being one-third of the brief's grading criteria — a finding an AI-only pass would likely have reported and moved past. Instruction was to keep pushing on *why*, past the first plausible-sounding answer, which is what actually produced the diagnosis: a partial-correlation check, then a synthetic off-topic-pair test (0.480 vs. 0.198 relevance for real vs. mismatched pairs) and a TF-IDF baseline comparison (0.012 correlation vs. the embedding's 0.123), both added to Part 1's relevance section on instruction, not proposed independently. The eval-strategy and ceiling framing that Part 2/3 both build on also came from this Part 1 direction. The AI's own contribution here was smaller and more mechanical: a structural cleanup pass (duplicate header, empty cells, a typo, reordering) done on request, and translating findings into code once the question was already set.
- **Part 2:** the confusion matrix, the per-language/CEFR/confidence breakdowns, and the five improvement attempts were explicit asks, run and reported against instruction (two adopted — ensemble, strengthened abstention — three rejected with numbers: sample weighting, hyperparameter tuning, Frank & Hall ordinal classification). The ordinal-classification test and the stratified error slices were proposed within that direction, not requested first.
- **Part 3:** LoRA, focal loss, and quantization were explicit asks. The prompt-inclusion question was direction-driven end to end and is the clearest example of persistent direction producing more rigor than one test would have: instruction to test whether adding the prompt (and later, language) to the transformer's text input helps, run as background training jobs while other work continued, repeated four times on MiniLM after each result still left the question open, then extended to a second backbone (XLM-R-base) on direct instruction — the test that reversed the conclusion (below). The value wasn't the AI catching its own mistake on the first pass; it was direction that kept the question open past the point the AI was ready to call it closed.

**Three concrete things the AI got wrong:**
1. **An over-generalized claim, caught by testing further rather than trusting the pattern so far:** after four MiniLM tests all showed adding the prompt hurt, the AI stated this as settled — "not open for revisiting without new training data." Direction to test a second backbone (XLM-R-base) showed the opposite trend on that backbone (QWK rising as context was added, see `REPORT.md`'s "Part 3's input design"), proving the original claim was backbone-specific, not a fixed property of the dataset. Corrected in both Part 3's notebook and the report rather than left standing. The most useful of the three, because it's a reasoning error, not an infrastructure one — a reminder that "consistent across N tests" still needs "and I varied the right thing" before it's a general claim.
2. **A real crash:** XGBoost's `.fit()` after a PyTorch/LoRA training loop segfaulted (torch/xgboost OpenMP conflict). Root-caused by bisecting the script; fixed with `OMP_NUM_THREADS=1`/`KMP_DUPLICATE_LIB_OK=TRUE` before any imports, `torch.set_num_threads(1)`, `n_jobs=1` — now in Part 3's first cell and `setup_check.py`.
3. **Focal loss with class-`alpha` reweighting** looked correct by the textbook recipe but destabilized training (QWK oscillating epoch to epoch). Caught by watching the predicted-class distribution swing rather than settle, not by trusting the standard recipe. Fixed by dropping `alpha`, keeping `gamma`.
